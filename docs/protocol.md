# Протокол HyperX Alloy Origins: что известно

Устройство: `03F0:0591`, `HP, Inc HyperX Alloy Origins`.

Документ разделён на две части: проверенные факты и гипотезы. Всё из
первой части воспроизводится на живом устройстве, всё из второй — нет.

## Интерфейсы USB

| Интерфейс | Драйвер | Endpoint | Дескриптор | Назначение |
|---|---|---|---|---|
| 0 | usbhid → hidraw | EP 1 IN | 65 байт, обычная клавиатура | нажатия; **принимает Set_Report** |
| 1 | usbhid → hidraw | EP 2 IN | 164 байта | мультимедиа + вендорные коллекции |
| 2 | usbhid → hidraw | EP 3 IN | 37 байт | дополнительные клавиши |
| 3 | **нет драйвера** | EP 4 OUT | 31 байт, вендорный | канал управления |

Интерфейс 3 не занят ядром, поэтому его можно захватить из пространства
пользователя через usbfs (`/dev/bus/usb/BBB/DDD`) — там же, где мы уже
делаем `USBDEVFS_RESET`. Права те же, root не нужен.

Дескриптор отчётов интерфейса 3 (получен контрольной передачей
`GET_DESCRIPTOR`, тип `0x22`):

```
06 90 ff     Usage Page (вендорная 0xFF90)
0a 00 ff     Usage (0xFF00)
a1 01        Collection (Application)
15 00        Logical Minimum 0
26 ff 00     Logical Maximum 255
75 08        Report Size 8
95 40        Report Count 64
09 02  81 02   INPUT   64 байта
09 03  91 02   OUTPUT  64 байта
0a 00 ff b1 02 FEATURE 64 байта
c0
```

Report ID не объявлены — отсюда наши 65-байтные буферы hidraw:
первый байт это номер отчёта (`0x00`), дальше ровно 64 байта полезной
нагрузки.

## Что подтверждено на устройстве

1. **Set_Report принимает только интерфейс 0.** На интерфейсах 1 и 2
   `HIDIOCSFEATURE` отвечает `EPIPE`. Наш клиент поэтому и работает
   через `hidraw0`.

2. **Get_Report работает только на интерфейсе 3.** На 0, 1 и 2 —
   `EPIPE` при любом Report ID и любой длине. То есть до сих пор мы
   писали вслепую: канал чтения существует, но на другом интерфейсе.

3. **Чтение возвращает последний записанный пакет.** Проверено:
   отправляем `81 11 22 33 ×16` — читаем его же; отправляем
   `81 44 55 66 ×16` — читаем его же.

4. **Байты 2 и 3 принадлежат firmware.** Что бы мы туда ни записали,
   при чтении там всегда `00 01`. Проверено записью `0x22 0x33`,
   `0x55 0x66` и `0x00 0x55` — во всех случаях читается `00 01`.
   Значение постоянное и от команды не зависит, так что это не код
   результата, а скорее признак версии или готовности.

5. **После `USBDEVFS_RESET` буфер принимает одно и то же содержимое:**

   ```
   81 08 00 01  81 00 00 00  81 00 00 00  81 08 08 10
   81 08 08 10  81 08 08 10  81 08 08 10  81 08 08 10
   81 00 00 00  81 08 08 10  81 08 08 10  81 00 00 00
   81 00 00 00  81 08 08 10  00 00 00 00  00 00 00 00
   ```

   Это не то, что мы писали последним (мы писали нули). Значит буфер
   восстанавливается самой клавиатурой при инициализации — вероятно, из
   её собственной памяти.

## Разбор установщика NGENUITY 2.11.0.0

Снять трафик не удалось, и вот почему: установщик — это .NET-обёртка
вокруг **APPX/MSIX-бандла**, то есть NGENUITY это UWP-приложение. Модели
приложений WinRT в Wine нет, запустить его под Linux нельзя ни в каком
виде. Остаётся виртуальная машина с Windows 10+ и пробросом USB.

Зато пакет разбирается статически. Путь: PE → секция `.text` → ZIP64 по
записи `PK\x06\x06` → `Setup_2.11.0.0_scale-125.msix` → 709 файлов.

Что это дало:

* Пути устройств: `HID#VID_03F0&PID_0591&MI_03` и
  `HID#VID_03F0&PID_0591&MI_01&Col05`. NGENUITY тоже работает через
  интерфейс 3, а коллекцию 5 интерфейса 1 слушает как канал событий.
* Имена операций: `keyboard.lights.saveToDevice`,
  `DeviceOnboardProfileChangedCommand`, `KeyboardMain.SwitchOnboardProfile`,
  `get_OnBoardProfileNumberOfCurrentDevice`. Аппаратные профили в
  приложении есть и они нумерованные.
* Перечень классов эффектов клавиатуры в порядке объявления:
  `Paint`, `Solid`, `Breathing`, `Cycle`, `Wave`, `Stacking`, `Confetti`,
  `Explosion`, `TriggerBase`, `Blaze`, `Fade`, `Fireworks`, `Implosion`,
  `Swipe`, `Twilight`, `Sun`, `Hourglass`.
  **`KeyboardPaintEffect`** — это и есть DIY: покраска клавиш вручную.

Чего разбор не дал: самих байтов команд. `NGenuity2.dll` собран
.NET Native (AOT), IL там нет. Байтовых шаблонов пакетов в данных тоже
нет — ни одного блоба, начинающегося с `04 F2`, а все 18 совпадений
`04 f2` в `.text` оказались смещениями rip-relative и SSE-инструкциями.
Значит пакеты собираются вычислениями в коде, и без дизассемблера
7 МБ AOT их не достать.

## Гипотезы, требующие проверки

Пакет прямого режима — `04 F2 00 00 00 00 00 00 09`. Разумное чтение:

* байт 0 = `0x04` — класс команды («подсветка»);
* байт 1 = `0xF2` — команда «выбрать режим»;
* байт 8 = `0x09` — **номер режима**.

Если так, значения 0…8 в байте 8 — это встроенные эффекты клавиатуры, и
один из них соответствует `KeyboardPaintEffect`, то есть DIY. Тогда
запись картинки в память свелась бы к «выбрать режим Paint + залить
цвета», а поток кадров стал бы не нужен.

Проверять это нужно, **глядя на клавиатуру**: обратной связи от firmware
у нас нет — статусное слово постоянно.

## Риск

Перебирать байты 0 и 1 вслепую нельзя. В пакете `Assets/Firmware/`
установщика лежат прошивки, а в приложении есть `FWUpdater.dll` — значит
где-то в этом же пространстве команд живёт вход в загрузчик. Случайно
попасть в него означает получить клавиатуру, которую придётся
перепрошивать из-под Windows.

Байт 8 при неизменных `04 F2` — это перебор внутри уже известной
команды, и худший исход здесь — клавиатура переключится на свой
встроенный эффект. Это откатывается сбросом USB или Fn-комбинацией.
